## 1. 项目架构图谱

本项目采用 **Monorepo** 结构，使用 `npm workspaces` 管理依赖。前后端分离，主要分为三个前端应用和一个后端服务。

### 目录结构

```text
root/
├── docs/                      # 项目文档 (包含架构图与上下文)
├── packages/                  # 前端工作区 (Vue 3 + Vite)
│   ├── website/               # 官网前台 (面向公众)
│   ├── management/            # 管理后台 (核心 CRM 业务，面向员工)
│   ├── customer-portal/       # 客户门户 (面向签约客户)
│   └── shared/                # 共享模块 (类型定义、工具函数、UI组件)
│
├── backend/                   # 后端服务 (Express + Prisma)
│   ├── prisma/                # 数据库模型定义 (PostgreSQL)
│   ├── src/
│   │   ├── controllers/       # 业务逻辑控制器
│   │   ├── routes/            # API 路由定义
│   │   └── services/          # 核心业务服务层
│
└── package.json               # 根依赖管理
```

### 模块依赖关系

- **@tonghai/shared** 被所有前端包 (`website`, `management`, `customer-portal`) 引用，确保类型 (`types`) 和组件的一致性。
- **@tonghai/backend** 独立运行，提供 RESTful API，各前端应用通过 Axios 与其交互。

## 3. 核心业务逻辑

项目核心围绕 **CRM (客户关系管理)** 展开，最复杂的逻辑集中在后端 Service 层和数据库设计中。

### 关键数据流与算法
1.  **RBAC 权限系统 (基于数据库的模型)**:
    -   未使用简单的枚举，而是设计了 `Role` (角色) 和 `Permission` (权限) 多对多关联表。
    -   **复杂点**: 动态权限验证。后端中间件需要解析用户 Token，查询 DB 获取角色权限，与当前路由所需权限进行比对 (`backend/src/middlewares`)。
    
2.  **销售线索 (Lead) 到 客户 (Customer) 的转化**:
    -   **逻辑**: 线索 (`Lead`) 经过跟进 (`contacts`)，状态变更为 `CONVERTED` 时，触发转化逻辑。
    -   **操作**: 系统需在 `Customer` 表创建新记录，关联原 `Lead`，并可能初始化 `Project`。这涉及跨表事务处理，确保数据一致性。

3.  **用户体系与多端隔离**:
    -   `User` 表包含 `roleId`。
    -   **管理端**: 仅允许拥有 "ADMIN", "MANAGER", "SALES" 角色的用户登录。
    -   **门户端**: 仅允许关联了 `Customer` 实体的用户登录 (或独立表结构，需注意 `User` 表中的 `UserCustomer` 关联)。
